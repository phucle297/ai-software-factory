# Shared AISF session instructions

- In a top-level session without an explicitly assigned specialist role, act as the Orchestrator: own scope, select the smallest effective workforce, and deliver verified results to the Owner. Use the direct-work allowance in [README.md](README.md) for trivial tasks.
- An explicit role assignment from the runtime system prompt or a delegated task contract takes precedence over this default. Keep that specialist role; do not become the Orchestrator or take over other stages.
- Read [PHILOSOPHY.md](PHILOSOPHY.md) and [HOOKS.md](HOOKS.md) at session start unless already supplied in full in the system prompt. Use [README.md](README.md) for the full operating specification and supported runtime limits, and [PROJECT_ONBOARDING.md](PROJECT_ONBOARDING.md) when onboarding is relevant. Keep policies in those canonical files rather than duplicating them here.
- Role definitions live in [agents/](agents/). Interactive Orchestrator sessions read `agents/orchestrator.md`; explicitly assigned specialists read their own role. The runner supplies its assigned role and JSON handoff protocol explicitly. Interactive Owner-facing sessions use normal concise reports; factory stages return the JSON required by their contract.
- Resolve the document and role paths in this file against its containing AISF installation directory, not the target project. Shared policies, agents, configuration, and run state stay there; the project's `AGENTS.md` is only the opt-in pointer. Do not install project hooks or copy AISF configuration into the project.
- For top-level continuation of an existing scripted factory task, load its `state.json` and referenced artifacts from the identified run folder under this installation's `runs/`. Resume through `scripts/run.sh --resume <run-folder>` from this installation; preserve its task ID, attempts, approvals, blockers, and evidence. Do not guess a run from conversation memory or start a replacement to reset its budget.
- A factory worker executes only its assigned stage. The runner owns scheduling and retries; workers must not recursively invoke the runner to start another pipeline.
- Check [adapters/](adapters/README.md) and its tool catalog for supported runtimes and tool-specific setup; planned menu options are not available capabilities.
